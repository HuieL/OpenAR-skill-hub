# Contributing to the OpenAR Skill Hub

This repository is a static catalog. OpenAR reads `skills.json` at a pinned
commit SHA and verifies each entry's sha256 before use. There is no server, no
account, and no install script to run here.

## Adding an entry

1. Host your skill in your own repository (a `SKILL.md` plus optional
   `scripts/`, `references/`, `assets/`). This hub does not copy third-party
   repositories.
2. Create `entries/skills/<id>/entry.json` following
   `schemas/skill-entry.schema.json`. The required facts:
   - `id` — namespaced identity (e.g. `openra.diagram-design`), equal to the
     directory name, globally unique, never reused;
   - `source` — `owner/name`, the skill's subdirectory, and an exact 40-hex
     commit SHA. `main`/`latest`/mutable tags are never accepted as a pin;
   - `files` — the complete manifest of the skill's files at that revision,
     each with sha256 and size (cap: 2 MiB per entry);
   - `license` — SPDX id; the entry must state the license its content
     actually carries.
3. Run `python3 scripts/build-index.py` and commit the regenerated
   `skills.json` together with your entry.
4. Open a PR. CI runs `scripts/validate.py` (read-only, no secrets, no
   install step; it never executes anything from your entry).

Maintainer-owned small skills may host their content directly under
`entries/skills/<id>/skill/`; every hosted file must then be listed in `files`
with a matching hash. Symlinks are rejected everywhere.

## Attribution

Original author, OpenAR adapter, and registry submitter are three different
roles and are recorded separately: `authors` (the original creators, with
names and optional GitHub logins), `adapters` (who adapted it for OpenAR),
and `registrySubmitter` (who filed the entry). Submitting a manifest does
not make you an author; authorship is checked against the source repository's
commits, license, or README during review, and corrections go through a PR.

An adapted entry (non-empty `adapters`) also records `upstream`: the original
`repo`, the exact 40-hex `revision` the adaptation started from, and the
upstream `license` (plus `path` when the skill is not at the repo root).
Original maintainer-authored content hosted on this hub needs no `upstream`.
Summaries are display text and get edited or translated; provenance lives in
the structured field, not in the prose.

## What review means

`review.status` records what a human looked at, and `reviewedRevision` pins
which revision that covered. `unreviewed` is not an accusation and `reviewed`
is not a guarantee; neither grants anything on a user's machine. Declarations
inside a `SKILL.md` (such as `allowed-tools`) are claims, not approvals.

## Curated publications (HUB-09 lockstep)

A curated skill ships twice: as the reviewed compiled body inside the
OpenAR CLI and as its `hub.<name>` publication here. Same version, same
bytes: a publication at version `v` must be byte-identical to the
compiled curated body at `v`. Version bumps are lockstep — the curated
data and the hub entry move in the same change. The entry packages the
curated spec's pinned upstream (repo, exact commit, path prefix,
license) as its `source` (verbatim carry) or `upstream` (vendored
adaptation). `ora hub audit-curated` reports drift; a divergent body at
the same version is re-published, never silently resolved.

## Updates and removal

A new upstream revision is a new `source.revision` plus a new `files` manifest;
older revisions stay in git history. Deprecation or a high-risk marking changes
`review.status` with a reason — entries and history are not silently deleted.

## Community data

`community/` holds the cross-registry community data (skills and,
eventually, extensions referenced as `kind:id` — e.g. `skill:hub.hallmark`):

- `featured.json` — maintainer-curated picks with a reason, a curator and
  a date. Edited by PR; being featured is not a safety review.
- `collections.json` — curated collections (title, description, curators,
  member entries). Edited by PR; a collection references entries, it
  never copies content, and joining one installs nothing.
- `creators.json` — a generated projection of the credit fields
  (authors / maintainers / contributors / adapters / registrySubmitter)
  across entries. Regenerate with `python3 scripts/build-community.py`
  (add `--extensions <path>` to a checkout of OpenAR-extension-hub to
  include extension credits). Never hand-edit.
- `discovery.json` — New (first recorded in this registry, from git
  history), Recently Updated, and Trending from public GitHub signals
  (stars/forks snapshot; stars are not install counts). Generated by
  `python3 scripts/build-discovery.py`. Never hand-edit. The
  `discovery` workflow regenerates and validates it on dispatch and
  uploads the result as an artifact; it never writes to the repository —
  a changed snapshot reaches main only through the normal review flow.

`scripts/validate.py` checks all four files on every PR: structure,
handle formats, and that every `skill:` reference matches a real entry.
`extension:` references are shape-checked here and existence-checked at
generation time.
